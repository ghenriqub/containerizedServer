Inception

Oito serviços, cada um selado no seu container, ligados por uma rede privada que não existe fora desta máquina. Todo o tráfego web entra por uma única porta. Esta página descreve o que está lá dentro e porque foi montado assim.

Corte transversal

Nenhum serviço web publica porta própria: tudo o que chega ao site passa primeiro pelo nginx, que termina o TLS e decide para onde encaminhar. Só o ftp e o uptime-kuma abrem portas próprias no host, o que o subject permite aos serviços bónus. O container que serve esta página está assinalado.

Todas as imagens são construídas a partir de debian:bookworm. Nenhuma vem pronta de um registry.

Decisões

Máquina virtual ou container

Uma máquina virtual emula hardware e arranca um kernel próprio; um container é um conjunto de processos do kernel do host, isolados por namespaces e cgroups. É por isso que um container arranca em milissegundos e ocupa dezenas de megabytes — mas partilha o kernel, logo um escape de container é um problema do host. Aqui usam-se as duas coisas em camadas: a VM isola o projecto da minha máquina, os containers isolam os serviços uns dos outros.

Secrets ou variáveis de ambiente

Uma variável de ambiente fica visível em docker inspect, é herdada por todos os processos filho e lê-se em /proc/PID/environ. Um secret é montado como ficheiro em /run/secrets, só no container que dele precisa, e nunca entra nas camadas da imagem. As passwords vão por secret; os nomes de bases de dados e domínios, que não são segredo, vão por .env.

Rede bridge ou rede do host

Com network_mode: host os containers partilhariam a pilha de rede da máquina e todas as portas ficariam expostas — o 3306 do MariaDB incluído. Numa bridge dedicada os serviços falam entre si por nome, resolvido pelo DNS interno do Docker em 127.0.0.11, e só sai para fora o que for explicitamente publicado. Publicamos o 443 e mais nada.

Volume nomeado ou bind mount

Um bind mount aponta para um caminho do host e traz consigo os donos e as permissões desse caminho, o que costuma acabar em conflitos de UID dentro do container. Um volume nomeado é gerido pelo Docker, tem ciclo de vida próprio e sobrevive a docker compose down. O subject exige volumes nomeados mas com os dados em /home/ghenriqu/data, e é para isso que serve o driver_opts.
