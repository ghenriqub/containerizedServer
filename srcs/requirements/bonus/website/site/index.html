Inception

Eight services, each sealed in its own container, joined by a private network that does not exist outside this machine. All web traffic enters through a single port. This page describes what is inside, and why it was assembled this way.

Cross-section

No web service publishes a port of its own: everything that reaches the site goes through nginx first, which terminates TLS and decides where to route it. Only ftp and uptime-kuma bind their own host ports, which the subject allows for bonus services. The container serving this page is marked.

Services

Every image is built from debian:bookworm. None is pulled ready-made from a registry.

Decisions

Virtual machine or container

A virtual machine emulates hardware and boots a kernel of its own; a container is a set of processes on the host kernel, isolated by namespaces and cgroups. That is why a container starts in milliseconds and costs tens of megabytes — but it shares the kernel, so a container escape is a host problem. This project uses both, in layers: the VM isolates the project from my machine, the containers isolate the services from each other.

Secrets or environment variables

An environment variable is visible in docker inspect, inherited by every child process, and readable in /proc/PID/environ. A secret is mounted as a file under /run/secrets, only in the container that needs it, and never lands in an image layer. Passwords go through secrets; database names and domains, which are not confidential, go through .env.

Bridge network or host network

With network_mode: host the containers would share the machine's network stack and every port would be exposed — MariaDB's 3306 included. On a dedicated bridge the services reach each other by name, resolved by Docker's internal DNS at 127.0.0.11, and only what is explicitly published leaves the host. We publish 443 and nothing else.

Named volume or bind mount

A bind mount points at a host path and drags its ownership and permissions along, which usually ends in UID conflicts inside the container. A named volume is managed by Docker, has its own lifecycle and survives docker compose down. The subject asks for named volumes but with the data under /home/ghenriqu/data, which is what driver_opts is for.
